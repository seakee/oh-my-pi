`task_list` never takes a turn of its own: emit it in the same response as your next real tool call (parallel tool calls), with `create` alongside the first read or action and `done`/`start` alongside the next action or check. A response whose only call is `task_list` wastes a full model round trip.
Items are identified by their verbatim text rather than generated IDs (such as `task-1`). Keep `item` and `group` names unique and stable; if text is lost, call `view` rather than guessing.
`append` requires `items`; an omitted `group` uses the in-progress item's group, else the first pending item's group, else the last group, else a new `Tasks` group. Supply `group` to target another group; an empty name is invalid.
Before starting work, call `create` for 3+ steps, requested task sets, or new instructions. List every user item separately (grouped, numbered, bulleted, or N items) rather than omitting items or keeping leftovers in memory.
After a successful update, when no item is active the earliest pending item starts in group order; when multiple are active, only the earliest stays active. Completing items out of order may rewind the pointer but never reopens completed items. Mark items done immediately and follow group order.
